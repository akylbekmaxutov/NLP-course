Lecture 10

AI Agents

In Lecture 9 we handed the model a document and it answered. Here we hand it a set of tools and let it decide what to do with them. That one change — the model choosing the next action instead of following our pipeline — is the whole of what people mean by an agent, and it brings a new kind of bug and a new kind of bill.

Learning goals

By the end of this lecture you can…

Say what an agent is

And, more usefully, what it is not: a fixed pipeline with a model in it is not an agent, however many steps it has.

Write the loop

Twenty lines, no framework. Ask, check for tool calls, run them, append the results, ask again.

Design a tool

A function, a JSON schema, and a sentence saying when to use it. The sentence is a prompt and it decides whether the agent works.

Read a trace

Tell a model that reasoned badly from a tool that failed, and know which of the two to fix.

Predict the bill

Every step resends the whole history. Know why seven steps cost five times what two steps cost, not three and a half.

Put guardrails on it

Step limits, argument validation, errors as data, and never eval. An agent is a loop that spends your money.

Every trace on this page is real. The agent in code_files/lesson10/ was run against gpt-4o-mini on 24 September 2026 and the steps, token counts and timings are copied out of those runs — including the ones where it got things wrong.

Theory · The idea

Pipeline, or agent?

Lecture 9’s RAG system had four steps and not one of them was a decision. Embed the question, fetch five passages, build the prompt, generate. Every question took exactly that path, because we wrote that path.

An agent is a loop in which a language model chooses an action, sees the result, and chooses again, until it decides it is finished. The actions are called tools: ordinary functions you expose to it.

Three things this buys, and what each one costs
it can do things
A model on its own produces text. A model with tools can look up a forecast, convert money, or send an email. The cost is that it can now do something wrong, not merely say something wrong.
it adapts the number of steps
Easy question, one call; awkward question, seven. Measured here: the same agent answered one question with no tools at all and another with seven calls. The cost is that you cannot predict the bill from the question.
it recovers
When a tool returns an error, it can try something else — and it did, twice, in the runs below. The cost is that it can also loop, and something has to stop it.

If your task always needs the same three steps, write the three steps. A pipeline you can read is worth more than an agent you have to supervise.

Practice · The mechanism

The loop, in twenty lines

There is no framework in this folder and there does not need to be. An agent is a while loop around the chat call you already know from Lecture 9. 

messages = [{"role": "system", "content": SYSTEM},
            {"role": "user",   "content": question}]

for step in range(MAX_STEPS):
    response = client.chat.completions.create(
        model=model,
        messages=messages,
        tools=tools.openai_tools(),     # the schemas, sent every turn
        tool_choice="auto",             # the model decides whether to call one
    )
    message = response.choices[0].message
    messages.append(message)            # the assistant turn, verbatim

    if not message.tool_calls:          # plain text = it is finished
        return message.content

    for call in message.tool_calls:     # it may ask for several at once
        result = tools.call(call.function.name,
                            json.loads(call.function.arguments))
        messages.append({"role": "tool",
                         "tool_call_id": call.id,
                         "content": json.dumps(result)})
The five things that matter here
tools=
The JSON schemas go in every request, not just the first. The model has no memory between calls; each turn it is told afresh what it can do.
tool_choice="auto"
The model may call a tool or answer directly. Forcing a call with "required" is occasionally useful and usually a sign the task is a pipeline.
append the assistant turn verbatim
Including its tool_calls. Each tool reply is matched to a call by tool_call_id, and the API rejects the next request if they do not line up.
no tool_calls means done
That is the whole stopping condition. The model signals completion by simply replying with text.
range(MAX_STEPS)
A while True here is a bill with no upper bound. Ours is 8.

Practice · Tools

A tool is three things

A function, a schema, and a sentence. Students write the first, tolerate the second, and skip the third — and the third is the one that decides whether the agent works. 

"geocode": {
    "fn": geocode,
    "schema": {
        "name": "geocode",
        "description": "Look up a place: coordinates, country, population, "
                       "elevation and timezone. Use this whenever you need "
                       "facts about a city rather than guessing them.",
        "parameters": {
            "type": "object",
            "properties": {
                "place":   {"type": "string", "description": "City or town name, e.g. Shymkent"},
                "country": {"type": "string", "description": "Optional ISO country code, e.g. KZ"},
            },
            "required": ["place"],
        },
    },

The six tools

The agent is a travel assistant for Kazakhstan that knows nothing. Every fact in its answers is fetched while you watch. That is what an agent is, and it also means this lecture states nothing about Kazakhstan it cannot source.

What to notice in eleven seconds of work
it chose days=7
Nobody asked for a week. The question said “what is the weather” and the schema said 1 to 16; the model picked. Agents make small unrequested decisions constantly, and this is the benign kind.
it answered in Kazakh
The tool results came back in English JSON. Translation on the way out is free and needed no instruction.

The distance_km tool returns a warning that road distance is longer, and that warning reached the user. A field in a tool result is a message to the model: use it.
575 then 999
Two turns, and the second cost 74% more than the first, because the first turn plus both tool results were re-sent inside it.
Result · Failure

When it goes wrong, and fixes itself

This is the run that justifies the whole architecture. A Russian question, a tool that could not find the place, and an agent that worked around its own broken tool without being told how. 

Q: Что такое Чарынский каньон и далеко ли он от Алматы?

[1] wikipedia(topic='Чарынский каньон', lang='ru')
    -> {"title": "Чарынский каньон", "summary": "Чары́нский каньо́н — протянувшийся на 154 км ...
[2] distance_km(origin='Алматы', destination='Чарынский каньон')
    -> {"error": "no place called 'Чарынский каньон' was found. Try the Latin spelling ..."}
[3] geocode(place='Charyn Canyon', country='KZ')
    -> {"name": "Charyn Canyon National Park", "latitude": 43.3501, "longitude": 79.0696, ...}
[4] distance_km(origin='Алматы', destination='Чарынский каньон')
    -> {"error": "no place called 'Чарынский каньон' was found. ..."}
[5] distance_km(origin='Almaty', destination='Charyn Canyon National Park')
    -> {"from": "Almaty", "to": "Charyn Canyon National Park", "straight_line_km": 175.0, ...}

5 tool calls, 4751 prompt tokens, 321 output tokens, 12.9 s
prompt tokens per turn: 572 -> 903 -> 1014 -> 1088 -> 1174
Three separate lessons in one trace
the error message did the teaching
The tool did not just fail, it said “try the Latin spelling, for example Almaty, Astana, Shymkent”. The model read that and geocoded in Latin at step [3]. An error string is a prompt too.
it repeated a known failure
Step [4] is identical to step [2], which had already failed and was still visible in the history. Agents do this, and it is why a step limit is not optional.
the real fix was in the tool, not the model
The first version of geocode only searched in English, so a Kazakh question spent four of eight steps failing to find its own cities. It now tries English, Russian and Kazakh, then transliterates. Same model, same prompt, half the steps.

When a trace looks bad, ask which half is at fault. Here it was the tool, and no amount of prompt engineering would have fixed it.

Result · Restraint

The cheapest correct answer uses no tools

Q: What will the weather be in Astana on 1 March next year?

ANSWER
I can only provide weather forecasts for up to 16 days in advance.
Unfortunately, I cannot give you the weather for March 1st of next year.

0 tool calls, 572 prompt tokens, 52 output tokens, 2.4 s

The system prompt says forecasts only reach about two weeks ahead and that the agent should say so rather than invent one. It did, without calling anything. Knowing when not to act is a capability, and it is the one most agent demos never show: 572 tokens against 6 451 for the most expensive run on this page.

Notice also what it did not do: it did not call weather_forecast with a made-up date and then paraphrase whatever came back. A tool that is called with nonsense usually returns something, and something is exactly what a fluent model needs to produce a confident wrong answer.

Result · Efficiency

Four calls in two turns

A comparison question needs the same two tools twice. The model asked for all four at once, and that costs far less than asking four times. 

Q: Compare Almaty and Shymkent: population, elevation, and the weather this week.
   Which is warmer?

turn 1  ->  geocode(Almaty), geocode(Shymkent),
            weather_forecast(Almaty, 7), weather_forecast(Shymkent, 7)
turn 2  ->  the answer

4 tool calls, 2052 prompt tokens, 418 output tokens, 6.8 s
prompt tokens per turn: 580 -> 1472

The conclusion it reached is checkable, which is the point of doing it this way: “Shymkent is slightly warmer than Almaty, 26.7 °C against 26.5 °C” — two numbers that came out of the forecast tool, not out of the model.

Result · Money

What a loop costs

Seven questions, one agent, one model. This table is the single most useful thing on the page, because it is the part people do not expect until the invoice arrives.

Why it grows the way it does
each turn resends everything
Turn n carries the system prompt, the question, and every assistant and tool message so far. The longest run went 588 → 669 → 728 → 822 → 1 055 → 1 274 → 1 315 tokens.
so the total is a sum, not a product
Roughly steps × average history, and the average history itself grows with steps. Doubling the steps more than doubles the bill: 2 turns cost 1 574, 7 turns cost 6 451 — 3.5× the turns for 4.1× the tokens.
the tool schemas are in every turn too
Our six schemas are about 500 tokens, resent on all seven turns of the worst run. Twenty tools would have cost more than the conversation.
a failure is charged twice
The failed call costs a turn, and its error message then sits in the history being resent for the rest of the run.

Lecture 8 showed how to compute a bill from a token count and a published rate; the arithmetic is unchanged here. What changes is that you can no longer predict the token count from the question, because the model decides how many turns to take.

Result · Honesty

The instruction it ignored

The system prompt contains this line, in capital-letter spirit if not in capitals: “Use calculate for every sum, total or per-day figure. Do not do arithmetic in your head.” 

Q: I have 500 USD for three days in Shymkent. What is that per day in tenge?

[1] convert_currency(amount=500, from_currency='USD', to_currency='KZT')
    -> {"converted": 222439.02, "rate": 444.878043, "rate_date": "Thu, 24 Sep 2026 ..."}
[2] calculate(expression='500/3')
    -> {"result": 166.666667}

ANSWER
500 USD is approximately 222,439.02 KZT at the exchange rate of 444.88 KZT per USD
on September 24, 2026.

For three days, that amounts to about 166.67 USD per day, which is approximately
74,146.34 KZT per day.

Count the divisions. It called calculate for 500/3 and then produced 74 146.34 — which is 222439.02 / 3 — without calling anything. It did the second division in its head, in direct contradiction of its instructions.

And the answer is correct. 222 439.02 ÷ 3 = 74 146.34 exactly. That is what makes this worth a section: the failure is invisible in the output. You only see it in the trace, and only if you count. An agent that follows its instructions 90% of the time looks identical to one that follows them always, until the 10% lands somewhere that matters.

What you would actually do about it
measure it
Run twenty money questions and count how many arrive at a number with no matching calculate call. Lecture 9’s rule again: an unmeasured claim about a prompt is an opinion.
make the tool the only path
Give convert_currency a divide_by argument, so the per-day figure comes back from the tool that already has the number. The best fix for “it did not use the tool” is usually a better tool.
check afterwards, in code
Pull the numbers out of the final answer and verify each one appears in some tool result. Ten lines, and it catches exactly this.
do not just shout in the prompt
“ALWAYS use the tool” in bold capitals is the reflex, and it is the weakest of the four.
Practice · Robustness

Six ways the loop breaks

Every one of these is tested in the folder, because an agent meets all of them in its first hour of real use.

Failure modes and what the agent receives
What happensWhat the agent gets back
It invents a tool: book_a_hotel{"error": "there is no tool called 'book_a_hotel'. Available: geocode, distance_km, …"}
Arguments are not valid JSON{"error": "arguments were not valid JSON: '{not json'"}
Wrong argument names{"error": "wrong arguments for distance_km: got an unexpected keyword argument 'city_a'"}
The API is down (a real 503 happened mid-run){"error": "could not reach api.open-meteo.com (HTTP Error 503)"}
calculate("__import__('os').system('echo pwned')"){"error": "only + - * / // % ** and numbers are allowed"}
It never stops calling toolsthe loop halts at MAX_STEPS = 8 and reports what it has
The four rules behind that table
errors are data, never exceptions
Every tool returns {"error": ...} instead of raising. A tool that raises kills the loop and throws away the work already paid for; a tool that returns an error lets the model try something else, which is what it did at step [3] of the Charyn run.
write error messages for the model
“try the Latin spelling, for example Almaty, Astana, Shymkent” is not for a log file. It is a prompt delivered at the exact moment it is needed, and it is what produced the recovery.
never eval model output
The model is an untrusted source in exactly the way a user is — and in an agent it is worse, because tool results from the open internet flow into it. calculate walks the syntax tree by hand and accepts numbers and six operators.
cap the steps
Not defensive programming, arithmetic: a loop with no limit is an unbounded charge on your account, and models do repeat failed calls. We watched one do it.
Theory · Judgement

When not to build one

Agents are the most over-applied idea in the field right now. The test is simple: does the number of steps genuinely depend on the input?

Write a pipeline

Classify these reviews. Summarise this document. Translate this page. Answer from these five passages. The steps are always the same, so write them: you get lower cost, fixed latency, and a program you can test with an ordinary test.

Write an agent

Questions where you cannot know in advance what is needed: one lookup or six, this tool or that one, stop now or keep going. Our budget question needed seven calls; the forecast question needed none. No pipeline covers both.

What you give up by choosing the loop
predictable cost
Measured on this page: 572 to 6 451 prompt tokens for questions a user would consider equally ordinary. An 11× spread.
predictable latency
2.4 s to 17.2 s. If a person is waiting, that range is the product.
reproducibility
The same question can take a different path on a different day. Pin the temperature low, log every trace, and accept that a run is evidence rather than a proof.
easy testing
You can no longer assert on one output. You test the tools separately, and the loop against a scripted model — which is exactly how the six failure modes above are tested without spending a cent.

A useful order: prompt, then retrieval, then an agent, then fine-tuning. It is Lecture 9’s order with one more rung, and the rungs get more expensive as you climb.

In class

Knowledge check

Eight questions we answer together before finishing.

Question 1

A colleague says their RAG system is “an agent” because it has four steps. Are they right?

Show Answer

No. Steps are not decisions. If every question takes the same four steps, the path was chosen by the programmer and the thing is a pipeline. The test is whether the number of steps changes with the input: ours used 0, 2, 4, 5 and 7 tool calls on five questions.

Question 2

How does the loop know the agent has finished?

Show Answer

The model replies with text and no tool_calls. That is the entire stopping condition — there is no special “done” signal. Which is also why a step limit is needed: nothing guarantees the model ever chooses to stop.

Question 3

One run made 4 tool calls and cost 2 052 prompt tokens. Another made 5 and cost 4 751. Why is one extra call more than twice the price?

Show Answer

Because it is not the calls that cost, it is the turns. The 4-call run asked for all four at once, so there were two turns. The 5-call run chained them, so there were five turns, and every turn resends the whole history plus all six tool schemas. Batch independent lookups; chain only when step two needs step one’s result.

Question 4

A tool raises a Python exception instead of returning {"error": ...}. What breaks?

Show Answer

The loop dies and every token spent so far is wasted, the user gets a stack trace, and the model loses its chance to recover. Our Charyn run is the counter-example: the error came back as data, the model read the hint in it, switched to the Latin spelling and finished.

Question 5

The agent was told to use calculate for every sum. It divided 222 439.02 by 3 in its head and got the right answer. Is there a problem?

Show Answer

Yes, and the fact that the answer was right is the problem. The instruction failed silently; nothing in the output shows it. Next time the number will be harder and the answer will be wrong in exactly the same confident tone. Fix it with a better tool (let the conversion take a divide_by), or by checking in code that every number in the answer appears in some tool result.

Question 6

Why is calculate written with an AST walker instead of eval?

Show Answer

Because the expression is written by a model, and the model is reading text from Wikipedia and public APIs. That is an untrusted chain ending in your process. Asked to run __import__('os').system('echo pwned'), the tool replies only + - * / // % ** and numbers are allowed. With eval it would have run it.

Question 7

The agent answered a question about next March’s weather without calling any tool. Did it fail?

Show Answer

No — that was the best run on the page. The system prompt said forecasts reach about two weeks and that it should say so rather than invent one, and it did, for 572 tokens and 2.4 s. The failure mode to fear is the opposite: calling the tool with a nonsense date, getting something back, and paraphrasing it confidently.

Question 8

The agent kept failing on Kazakh city names. Would a better prompt have fixed it?

Show Answer

No. geocode searched the gazetteer in English only, so «Алматы» genuinely did not exist as far as the tool was concerned, and four of eight steps went on failing lookups. The fix was in the tool: try English, Russian and Kazakh, then transliterate. When a trace looks bad, decide first whether the model reasoned badly or the tool answered badly.

Practice

Practice tasks

Work in code_files/lesson10/. Everything here is one command or one small edit.

Task 1 — Reproduce the table

Run python3 agent.py --demo and compare your tool counts and token totals with the table above. They will not match exactly. Write one sentence explaining why that is expected rather than a bug.

Task 2 — Break a description

In tools.py, change geocode’s description to just “Looks up a place.” Ask three questions that need population figures. Does it still call the tool, or does it start guessing? You have just measured what a description is worth.

Task 3 — Force the arithmetic

Add a divide_by argument to convert_currency so a per-day figure comes back from the tool. Re-run the 500 USD question. Does the unsourced division disappear?

Task 4 — Lower the limit

Set --max-steps 2 and ask the Turkestan budget question, which needed seven. Read what comes back. Then decide what a real product should do when the limit is hit: apologise, answer partially, or escalate?

Task 5 — Add a tool

Write timezone_difference(place_a, place_b) using the timezone geocode already returns. Register it, then find a question that makes the agent choose it without being told to.

Task 6 — Audit the citations

Write a script that extracts every number from the final answer and checks it appears somewhere in the tool results for that run. Run it over the seven demo questions. How many unsourced numbers do you find besides the one on this page?

Task 7 — Two backends

Run the same question against OpenAI and against Lecture 9’s local 4 B model. Compare tool choice, step count and total tokens. Which parts of “being an agent” survive the smaller model?

Task 8 — A tool that lies

Make convert_currency return a rate ten times too large. Ask a budget question. Does the agent notice anything is wrong? Write two sentences on what this implies about trusting tool output.

Summary

Today we learned

  • An agent is a loop in which the model chooses the next action; steps alone do not make a pipeline into one
  • The loop is about twenty lines: ask with tools, run what it asks for, append the results, ask again
  • It stops when the model replies with text and no tool calls — so a step limit is not optional
  • A tool is a function, a JSON schema, and a description; the description is a prompt and decides whether the tool is ever used
  • Our agent knows nothing about Kazakhstan: every distance, forecast, rate and description was fetched at run time
  • The same agent used 0, 2, 4, 5 and 7 tool calls on five ordinary questions — you cannot predict the path from the question
  • Turns cost, not calls: 4 calls in 2 turns cost 2 052 tokens; 5 calls in 5 turns cost 4 751
  • Cost grew from 572 to 6 451 prompt tokens across seven questions, an 11× spread, and latency from 2.4 s to 17.2 s
  • Errors must be data, not exceptions — that is what let the agent recover from a failed lookup
  • Write error messages for the model: “try the Latin spelling” is what produced the recovery
  • Agents repeat failed calls: ours reissued an identical failing call it could still see in its own history
  • Never eval model output; calculate refused __import__('os').system(...)
  • It disobeyed its own instruction to use calculate, and got the right answer anyway — visible only in the trace
  • The best run on the page called no tools at all, because the honest answer was “I cannot know that”
  • The bad trace was the tool’s fault, not the model’s: fixing Kazakh place names halved the steps
  • Prompt, then retrieval, then an agent, then fine-tuning — in that order, because each rung costs more
